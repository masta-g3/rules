01 / PurposeFor maintainers and contributors

Shared instructions for AI coding work.

This repo is not an app. It holds the rules, skills, reviewer agents, and Pi extensions that tell coding agents how to plan, build, review, and record changes in your other projects.

Example request in your project

"Add dark mode. Plan it before changing code."

The app code lives in your project. This repo shapes how the agent works on it.

  1. 01
    A plan you can inspect

    Scope, decisions, and acceptance checks before any code changes.

  2. 02
    A change you can review

    Code plus verification, checked against the plan by the agent and a critic.

  3. 03
    A record you can resume

    Ticket status and plans in agent-work/, so a new session can continue.

Why the rules exist

Each rule answers a known agent failure, from PRINCIPLES.md and prompts/AGENTS.md.

  • Agents drift local and duplicate code→Reuse first; plan and code critics check fit
  • Agents over-build and over-abstract→Smallest viable change; functional style where it fits
  • Agents code defensively→No silent fallbacks or compat shims; let errors surface
  • Sessions lose context→One task per session; state lives in agent-work/
  • Agents decide design alone→Each step stops for the user; questions on material choices
  • Docs fill up with history→reflect keeps only current truth in docs/
Skills give instructions. Helpers, agents, and extensions support them.Next: workflow →

One ticket, three moments on disk.

Inside agent-work/

  • features.yaml: backlog. Statuses: pending, in_progress, done, abandoned, superseded.
  • plans/ and history/: active and finished plans.
  • tickets/<id>/: evidence or repro files, only when needed.
  • decks/: HTML explainers like this one.

Outside agent-work/

  • CONTEXT.md: what the project is and who it serves.
  • docs/: durable architecture and reference. Current truth only.
  • Tickets hold short facts. Plans hold scope and checklists. YAML never holds steps.
Ticket fields: title 1–3 words, subtitle 4–6 words, description one outcome sentence.Next: skills →

04 / Skills and agents

More than the six-step loop.

Each skill is a SKILL.md file with steps for one task. Ask for it by name. The six workflow skills are on slide 02; these are the rest.

  • project-initCreate agent-work/ scaffolding

Maintain

06 / Pi runtime

In Pi, the workflow is visible.

extensions/workflow-runtime/ shows where a session is in the loop, links it to a ticket, and publishes that state for dashboards such as pi-agent-hub.

auth-001 · ✓ Plan ─ ◉ Execute ─ · Review ─ · Reflect ─ · Commit ◇ meta
auth-001 · ✓ Plan ─ ◆ Focus turn 4 ─ · Review ─ · Reflect ─ · Commit
auth-001 · ✓✓✓✓✓ Commit complete
  • Simplified rail examples.
  • ✓ done position
  • ◉ current step
  • · later step
  • ◆/◇ Focus autonomous loop running
  • ◇ meta naming/attention model status
  • Ticket link

    /skill:plan-md auth-001 or /wf-ticket auth-001 links the ticket. The session takes the ticket title as its name.

  • Focus mode

    During execute, the agent can call start_focus to keep working across turns. It stops with end_focus (completed or blocked). Esc pauses it.

  • Next step shortcut

    Double-press Ctrl+Shift+→ to run the next skill with the linked ticket. /wf-todos shows the plan checklist.

  • Attention signals

    Questions and ready/blocked states are published so a dashboard can show which session needs you.

The rail shows position, not an audit. Rules works without Hub; publishing context does not give Hub ownership of Git or worktrees.
